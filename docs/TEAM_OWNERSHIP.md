# Team ownership and review

One Express server, one Supabase PostgreSQL database, and one centrally maintained migration stream serve all five modules. Existing Vite/Expo routes and mock data remain available while each team's API work proceeds.

| Owner | Frontend | Server folder | Data |
| --- | --- | --- | --- |
| 1. Volunteer Management | `apps/web/src/pages/{Volunteers,Teams}.tsx`, volunteer components, mobile volunteer profile/availability routes and components | `server/src/modules/volunteers` | Volunteer profiles/contact, availability, teams and membership. |
| 2. Food and Donor Management | `apps/mobile/src/app/donor`; future reviewed admin food views | `server/src/modules/food` | Donors, food requests/items, declaration and manual safety review. |
| 3. Pickup and Logistics Management | `apps/web/src/pages/Assignments.tsx`, `apps/web/src/components/assignments`, mobile volunteer assignment routes/components and future dispatch views | `server/src/modules/pickups` | Pickups, assignments, participants, reservations, status history and actual container/vessel plans. |
| 4. Vehicle Tracking and Management | Future `apps/web/src/components/tracking` and `apps/mobile/src/components/tracking` views, created only after route review | `server/src/modules/tracking` | Tracking consent, active-trip observations, location authorization and retention. |
| 5. Vehicle Details Maintenance | Future `apps/web/src/components/vehicles` registry, maintenance and assigned-person views, created only after route review | `server/src/modules/vehicles` | One canonical vehicle/driver registry, size and weight specifications, indicative vessel capacity, unavailability and maintenance history. |
| Integration maintainers | Cross-app Auth adapters, common API clients and cross-module `apps/web/src/pages/Dashboard.tsx` composition | `server/src/auth`, `server/src/db`, middleware, routes/index, config | Canonical people, shared contracts, SQL migrations, root dependencies, lockfile, CI, deployment and role policy. |

Module teams may propose schema and shared-contract changes, but only integration maintainers edit and merge centrally owned files after affected-owner review. No team duplicates `vehicles`, `people`, `assignments` or migration directories. A volunteer and driver can link to the same `person_id`; any approved employee-specific profile links to `people` rather than copying identity fields. Do not add an EMPLOYEE Auth role without a reviewed login requirement. Cross-module calls use reviewed service interfaces, not another module's repository or SQL tables. Food asks Pickup to cancel a dispatch in one transaction. Pickup coordinates Food readiness, Volunteer availability and Module 5 vehicle/driver eligibility before reserving resources. Module 4 obtains active-trip authorization from Module 3 and vehicle identity from Module 5. Module 5 obtains assigned volunteer/driver IDs from Module 3's `GET /api/v1/vehicles/:id/assignments` projection; it never stores another editable roster. Contact details come from the owning profile APIs.

The root `AGENTS.md` applies to all Codex contributors. `apps/mobile/AGENTS.md` adds Expo-specific guidance. Authentication, authorization, shared configuration, migrations, root dependencies and lockfile, shared contracts, CI and deployment require integration-maintainer review. CODEOWNERS currently names the GitHub repository owner for central paths; confirm review access and add team handles before enforcing branch protection. Pull requests identify owning team, affected teams, central files, contract/schema effects, UI screenshots when relevant, checks, and migration/rollback plan. Do not push domain work directly to main or develop.
